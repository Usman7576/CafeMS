# Load test: performance under attack

**No staff request failed, and the slowest 5% stayed under the limit, but response times did not meet the Week 4 example target of 10% slower.** During a flood of 19,198 attack requests from 50 addresses, 240 staff screen refreshes from six signed-in staff all succeeded, and the slowest 5% took 133.9 ms or less (limit 250 ms).

Generated by `npm run load-test -- --write` on 2026-11-09 (8 CPU threads, Node v24.19.0). It uses the real rate limits, real HTTP and a throwaway database, with the attack on its own thread. Timings vary with the machine's load, so run it on the production server for figures that count. Requirement SR-20.

| Measure | Staff alone | Staff during the attack |
| --- | --- | --- |
| Median response | 6.6 ms | 88.9 ms |
| 95th percentile | 9.3 ms | 133.9 ms |
| Failed requests | 0 of 240 | 0 of 240 |

**The attack:** 64 requests in flight at a time, from 50 addresses, mixing password guessing, booking-form spam and page loads. 10,714 of 19,198 attack requests (56%) were refused by the rate limits.

**Against the Week 4 example of "no more than 10% degradation":** the 95th percentile was 1338% slower under attack, so it does not meet that target on this machine. Each refused request still costs a little work, and on a single server process the staff requests share the CPU with the flood. Staff were never refused or timed out, which is the property the cafe needs; flood protection in front of the server, such as Cloudflare, is outside what the app itself can do (see OUT-OF-SCOPE.md).
