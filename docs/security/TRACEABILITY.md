## Use and misuse cases

| MC-01 | Sign-in | A waiter signs in with password and authenticator code. | An attacker with a leaked password tries authenticator codes until one works. | Three wrong codes lock the account for 15 minutes, and repeated failures raise an alert. | SR-03 | the right password alone does not reset the count, so authenticator codes cannot be guessed forever |
| MC-02 | Orders | A waiter edits their own order before the kitchen starts it. | A waiter changes the order ID to edit another waiter's order. | The order looks the same as one that does not exist (404). | SR-06 | one waiter cannot see or change another waiter's order |
| MC-03 | Billing | A cashier takes payment for a served table. | The cashier sends a lower total from the browser console. | The server ignores client totals and refuses the extra field. | SR-07 | a price or total sent by the browser is refused |
| MC-04 | Refunds | A manager refunds a wrong item. | A manager refunds a large bill to an accomplice. | Over Rs 5,000 a different person must approve with a fresh code; refund spikes raise an alert. | SR-10 | a large refund waits for a different person with a fresh code |
| MC-05 | Kitchen | The kitchen moves an order to Preparing and Ready. | A kitchen user tries to read prices or take a payment. | The kitchen receives no prices, and payment routes refuse the role. | SR-05 | the kitchen sees no prices or staff details, and follows the status order; a waiter and the kitchen cannot take payment (finding 7) |
| MC-06 | Public booking | A customer requests a table online. | A bot floods the form, or someone checks whether a number has booked. | A limit per address and a hidden field stop bots; the answer is the same either way. | SR-20 | a bot that fills the hidden field is told it worked, but nothing is saved; a repeat gets the same answer, so it cannot reveal who has booked |
| MC-07 | Reservations | A waiter looks up a booking by phone number. | A waiter collects customers' full phone numbers. | Waiters see masked numbers; full numbers need a Manager or Admin and are logged. | SR-12 | waiters see a masked phone; only a Manager or Admin can reveal it, with a log entry (finding 32) |
| MC-08 | Menu | An Admin uploads a photo of a dish. | An attacker uploads an HTML or script file named as a picture. | The file signature is checked, and the upload refused and recorded. | SR-13 | scripts, SVG, HTML and disguised files are refused and recorded |
| MC-09 | Staff administration | An Admin invites a new waiter. | One Admin secretly creates a second Admin account. | Any change affecting an Admin waits for a second Admin. | SR-10 | one Admin alone cannot create another Admin; a second Admin must approve |
| MC-10 | Audit log | An Admin reviews who changed a price. | Someone with database access edits an entry to hide a refund. | The chain check finds the change and raises an alert; the app account cannot edit entries. | SR-11 | detects edited details, a changed actor and a changed time |
| MC-11 | Reports | A manager exports today's sales. | A departing manager exports data again and again. | Exports are limited per person, recorded and alerted. | SR-19 | exports are logged, limited per person, and safe to open in a spreadsheet |
| MC-12 | Payments | The gateway confirms a card payment. | An attacker replays a captured approval callback. | Each signed callback is accepted once; a copy is refused and logged. | SR-15 | a copied gateway callback is accepted only once |
