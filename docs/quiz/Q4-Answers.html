D. Failure analysis and mitigation

1. Database failure (C4 fails)

  • Direct effects: C2 cannot read or save requests; C3 cannot check sessions or passwords; C5 cannot write history.
  • Indirect effects: in C1, users cannot sign in or out, list, submit, claim, resolve or reject.
  • Safe handling: the API returns 503 "database unavailable, nothing was saved". Each change and its history run in one transaction, so there is no half-saved record and no false success.
  • Can continue safely: static and public pages load; the liveness health check answers; data already committed stays safe on disk and is available again when the database returns.

2. Authentication failure (C3 fails, or the token is missing, invalid or expired)

  • Must stop: every protected operation: create, list, detail, history, claim, resolve, reject and every staff page. The system fails closed with 401 (not signed in) or 403 (wrong role) and never guesses the user or role.
  • Can continue safely: public pages (home, menu, public reservation form), static files and health checks. Stored records and history stay unchanged, because nothing is written without a verified identity.

3. Critical component and recovery

Critical component: C4, the database. It has the most dependents: C2, C3 and C5 directly, and C1 indirectly. It is the single point of failure; if it stops, every function stops.

Failure-handling strategy: run MongoDB as a 3-node replica set with automatic failover (deploy/docker-compose.ha.yml), with encrypted daily backups (npm run backup) and a tested restore.

Justification:

  • If the primary crashes, the other nodes elect a new primary in about 10 seconds, without manual work.
  • Majority write concern and transaction retries mean no committed data is lost.
  • During the switch-over the app shows 503 instead of saving partial data.
  • Backups cover the worst case, such as accidental deletion or ransomware.
